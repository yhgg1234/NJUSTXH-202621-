# 2.2 数据交付反馈

这次检查的是旧版 500 条数据生成的三个文件：

- `normalized_records.jsonl`
- `graph_import_batch.json`
- `quality_report.json`

先说一下整体结论：目前不是所有内容都要推倒重做。实体抽取结果、必备/加分技能的原文证据，以及部分常见技能的标准 ID 都可以继续使用。主要需要修改的是去重、岗位/技能标准化、图谱转换和质量统计程序，然后重新生成三份文件。

旧数据没有真实 `published_at`，继续写成 `null` 就可以，不要用抓取时间、文件时间或导出时间代替。这一批可以先做静态图谱，但不能生成月度/季度快照，也不能拿来做 3.1 动态演化。

建议先用最新的 48 条数据把下面的规则全部跑通，确认接口可以导入、结果可以回溯，再处理正式大批量数据。

## 一、`normalized_records.jsonl` 需要修改的地方

### 1. 先完成 JD 去重

当前 500 条记录中只有 496 个唯一 `jd_id`、471 个唯一 `content_hash`，说明既有重复 ID，也有正文完全相同的记录。质量报告目前仍把 500 条全部统计为有效记录，不太准确。

建议按下面的顺序处理：

1. 先按 `jd_id` 去重。同一 `jd_id` 重复出现时，只保留字段更完整的一条；
2. 再按 `content_hash` 检查重复正文；
3. 如果正文相同但来源、公司或发布时间不同，不要直接静默删除，要记录在重复映射表中；
4. 最终在质量报告中写清楚原始数量、重复数量、拒绝数量和有效数量。

可以另外输出一份类似下面的记录，方便后续审计：

```json
{
  "kept_jd_id": "external:JD000011",
  "duplicate_jd_ids": ["external:JD000620", "external:JD000778"],
  "reason": "same_content_hash"
}
```

### 2. 岗位需要真正做标准化

当前岗位数据基本是直接对原始岗位名生成 `job:hash-*`：

- `canonical_name` 全部等于 `raw_name`；
- `aliases` 只有原始名称；
- `canonical_id` 全部是哈希 ID；
- 500 条全部是 `is_new_candidate=true`；
- `alignment_confidence` 全部固定为 0.8；
- `level` 全部是 `unknown`。

这相当于完成了“生成 ID”，但还没有完成“同义岗位对齐”。

例如下面三个名称可以统一：

```text
Data Scientist
Data Scientist（数据科学家）
数据科学家
```

统一后可以写成：

```json
{
  "raw_name": "Data Scientist（数据科学家）",
  "canonical_id": "job:data-scientist",
  "canonical_name": "数据科学家",
  "aliases": ["Data Scientist", "Data Scientist（数据科学家）", "数据科学家"],
  "alignment_confidence": 0.95,
  "is_new_candidate": false
}
```

需要注意，“数据分析师”和“数据科学家”通常不是同一个岗位，不能因为名称接近就直接合并：

```text
Data Scientist / 数据科学家 → job:data-scientist
Data Analyst / 数据分析师   → job:data-analyst
```

遇到边界不清楚的岗位，可以结合职责和技能组合判断。例如标题是“数据分析师”，正文却主要是模型训练、特征工程和机器学习，可以降低置信度并设置人工审核，而不是强制映射。

比较稳妥的实现方法是维护一张岗位词典：

```json
{
  "job:data-scientist": {
    "canonical_name": "数据科学家",
    "aliases": ["Data Scientist", "数据科学家", "数据科学工程师"]
  },
  "job:data-analyst": {
    "canonical_name": "数据分析师",
    "aliases": ["Data Analyst", "BI数据分析师"]
  }
}
```

转换时可以按“精确别名匹配 → 清洗等级/语言后匹配 → 结合正文辅助判断 → 无法判断则进入候选池”的顺序处理。高级、资深、初级等信息尽量拆到 `level`，不要仅因为等级不同就创建新的标准岗位。

### 3. 正确使用 `is_new_candidate`

当前 472 个技能 ID 中，有 361 个 ID 在不同记录里同时出现 `true` 和 `false`，包括 Python、SQL、MLflow 等成熟技能。

`is_new_candidate` 的含义应该是：这个名称无法可靠映射到现有本体，需要人工确认。它不能表示“这个技能是不是本批次第一次出现”。

建议规则如下：

```text
能匹配已有标准实体 → is_new_candidate=false
无法匹配、临时生成候选 ID → is_new_candidate=true
同一个 canonical_id 在整个批次中的状态必须一致
```

像 Python、SQL、Docker 这类已经进入词典的技能，应始终为 `false`。候选技能建议统一放到一份待审核清单，审核通过后再加入正式词典。

### 4. 同一 JD 内相同技能要合并

目前有 8 条 JD 在同一条记录里重复出现相同的 `canonical_id`，主要是大小写差异，例如：

```text
Git / git
COAP / CoAP
WeNet / Wenet
Diffusion / diffusion
```

处理方式不是删掉其中一条证据，而是以 `canonical_id` 分组，统一名称并合并证据：

```json
{
  "canonical_id": "skill:git",
  "canonical_name": "Git",
  "aliases": ["Git", "git"],
  "evidence": ["证据片段1", "证据片段2"]
}
```

如果同一技能同时被抽成 `required` 和 `preferred`，按 `required > preferred > mentioned` 的优先级合并。

### 5. 相同技能 ID 只能有一个规范名称

当前存在下面这类情况：

```text
skill:xgboost → XGBoost / xGBoost
skill:git     → Git / git
skill:kafka   → Kafka / kafka
```

一个 `canonical_id` 应该固定对应一个 `canonical_name`，其他写法放入 `aliases`。建议从技能词典读取规范名称，不要直接使用当前记录第一次出现的写法。

### 6. 技能分类不能全部写成 `General`

当前 4625 个技能对象的 `category` 全部是 `General`，这个字段基本没有起到标准化作用。

可以先采用一套有限且稳定的分类，不必一开始分得特别复杂，例如：

- 编程语言：Python、Java、Go；
- 数据库与存储：MySQL、Redis、Milvus；
- 开发框架：FastAPI、Spring、React；
- 云与容器：Docker、Kubernetes；
- 数据与计算平台：Spark、Flink、Hadoop；
- 工程工具：Git、Jenkins、MLflow；
- 算法与方法：特征工程、推荐算法、深度学习；
- 大模型应用：RAG、Agent、Prompt Engineering；
- 数据分析与可视化：Tableau、Power BI、数据分析。

分类应放在技能词典中，同一个技能在不同 JD 中不能一会儿属于 A 类、一会儿属于 B 类。

### 7. `mentioned` 技能也尽量保留证据

当前 `required/preferred` 技能都有证据，这部分做得不错；但有 2387 个 `mentioned` 技能没有证据，涉及 443 条 JD。

`mentioned` 不进入岗位必备技能计算，但最好仍保留原文片段，便于判断它到底是岗位要求、业务场景还是普通背景词。如果确实无法提供，质量报告要注明 `missing_evidence` 的统计口径是不是只统计 `required/preferred`，否则写成 0 容易引起误解。

### 8. 2.1 已经提供的字段不能在2.2中丢失

岗位正文、经验、学历、来源平台和 URL 如果在 2.1 中已经存在，2.2 转换时必须继续保留。如果 2.1 本来就没提供，则保持 `null` 或省略，并在质量报告中统计，不要自行猜测。

简单来说：时间、URL、原文缺失可能是上游问题；岗位对齐、技能去重、候选状态和标准 ID 则属于 2.2 需要解决的问题。

## 二、`graph_import_batch.json` 需要修改的地方

### 1. 当前文件还不能直接导入

文件中有 205 条关系使用了：

```json
"type": "REQUIRES_TECH_STACK"
```

当前接口没有这个关系类型，调用 `/api/graph/import` 会返回 422。

现有契约采用的是：

```text
Job   -[REQUIRES_SKILL/BONUS_SKILL]-> Skill
Skill -[BELONGS_TO_STACK]-----------> TechStack
```

不能把 `REQUIRES_TECH_STACK` 直接改名为 `BELONGS_TO_STACK`，因为关系方向和端点含义不同。

建议这样处理：

- AWS、Linux、Docker、Kubernetes 等具体工具或平台优先建成 `Skill`；
- “云原生”“大数据技术栈”“机器学习工程栈”等技术体系建成 `TechStack`；
- 岗位通过 `REQUIRES_SKILL/BONUS_SKILL` 连接具体技能；
- 技能再通过 `BELONGS_TO_STACK` 连接所属技术体系。

例如：

```text
后端开发工程师 -[REQUIRES_SKILL]-> Kubernetes
Kubernetes     -[BELONGS_TO_STACK]-> 云原生
```

### 2. 必须生成 `Source` 节点

当前文件有 933 个实体节点、2096 条关系，但一个 `Source` 节点都没有；与此同时，`source_ids/evidence_ids` 引用了 496 个 Source ID。这些引用现在是悬空的，无法查看对应原始 JD。

去重完成后，每条有效 JD 都应生成一个 Source 节点，例如：

```json
{
  "id": "source:external:JD000008",
  "type": "Source",
  "name": "external:JD000008",
  "confidence": 1.0,
  "properties": {
    "jd_id": "external:JD000008",
    "document_type": "job_description",
    "content_hash": "sha256:...",
    "crawled_at": "2026-08-01T13:20:30+08:00",
    "source_platform": "...",
    "url": "..."
  }
}
```

旧数据没有发布时间时，省略 `published_at` 或明确保持为空，不要把 `crawled_at` 复制过去。

生成图谱后应检查：所有节点的 `source_ids`、所有关系的 `evidence_ids`，都能在 `nodes` 中找到对应的 Source 节点。

### 3. 同一岗位—技能不能同时生成必备和加分关系

当前有 378 组岗位—技能同时存在 `REQUIRES_SKILL` 和 `BONUS_SKILL`，例如同一个 Data Scientist → Python 同时生成了两条边。这会导致 2.3 重复显示，3.3 也可能重复计算。

聚合时建议按 `(job_id, skill_id)` 分组，分别统计：

```text
required_jd_count  = 标记为 required 的去重 JD 数
preferred_jd_count = 标记为 preferred 的去重 JD 数
skill_jd_count     = required 或 preferred 包含该技能的去重 JD 数
required_ratio     = required_jd_count / skill_jd_count
```

然后只生成一条关系：

```text
required_ratio >= 0.5 → REQUIRES_SKILL
否则                  → BONUS_SKILL
```

`mentioned` 不应进入岗位技能要求关系。

### 4. 关系属性需要保留聚合结果

目前静态岗位—技能关系基本没有 `properties`。建议至少保存：

```json
{
  "frequency": 12,
  "required_jd_count": 8,
  "preferred_jd_count": 4,
  "required_ratio": 0.6667,
  "importance": 0.8
}
```

`frequency` 应按包含该技能的去重 JD 数计算，不是关键词在正文中出现了多少次。`importance` 的计算方法要固定，并在文档或质量报告中写明。

### 5. Job 和 Skill 节点属性不能全部丢掉

当前 59 个 Job 节点的 `properties` 全部为空，472 个 Skill 节点也没有保存 `category`。这样即使 JSONL 中完成了标准化，2.3 和 3.3 仍然使用不到。

Job 节点建议写入有证据支持的字段：

```json
{
  "description": "...",
  "level": "mid",
  "min_experience_years": 2,
  "preferred_experience_years": 4,
  "education_required": "本科及以上"
}
```

Skill 节点建议至少写入：

```json
{
  "category": "云与容器"
}
```

没有可靠证据的字段可以省略，不要为了填满字段而写 0 或 `unknown`。

### 6. 没有时间时不要生成周期关系

这一点目前的处理方向是对的。旧数据 `published_at=null`，因此岗位—技能关系保持静态即可，不应生成 `period_key`、`period_start`、`job_jd_count` 或 `demand_ratio` 来伪装历史数据。

以后使用带真实发布时间的数据时，再按月度或季度聚合并生成周期关系。

## 三、还需要补充的交付文件

除三份主文件外，建议同时提供：

1. 岗位和技能标准词典及版本；
2. 旧 ID → 新标准 ID 的映射记录；
3. 被合并实体的别名记录；
4. 新候选实体及人工审核状态；
5. 重复 JD 的保留/合并记录。

例如：

```json
{
  "old_id": "job:hash-8a7a3f1bce",
  "new_id": "job:data-scientist",
  "reason": "alias_match",
  "confidence": 0.95,
  "review_status": "approved"
}
```

这样以后本体或词典升级时，可以解释为什么 ID 发生变化，也不会让 2.3、2.4、3.1、3.3 重新猜测映射关系。

## 四、建议的处理顺序

为了减少返工，可以按下面的顺序改：

1. 用最新 48 条数据读取2.1字段，先完成 JD 去重；
2. 建立岗位、技能和分类词典；
3. 逐 JD 生成并检查 `normalized_records.jsonl`；
4. 检查同一 JD 内是否存在重复 `canonical_id`；
5. 聚合生成唯一的岗位—技能关系；
6. 生成 Source 节点和其他实体节点；
7. 只使用当前接口支持的关系类型；
8. 生成 `graph_import_batch.json`；
9. 使用项目模型执行一次本地校验；
10. 根据实际结果生成 `quality_report.json` 和映射记录。

图谱文件可以用下面的方式做最基本的接口校验：

```powershell
python -c "import json; from pathlib import Path; from app.graph.models import GraphImportRequest; GraphImportRequest.model_validate(json.loads(Path('graph_import_batch.json').read_text(encoding='utf-8'))); print('校验通过')"
```

运行时需要确保 Python 能导入项目的 `app` 包，例如在项目根目录设置 `PYTHONPATH=backend`，或者进入 `backend` 目录运行。

- [ ] `is_new_candidate` 在同一实体上保持一致；
- [ ] 标准岗位不是全部 `job:hash-*`；
- [ ] 技能分类不是全部 `General`；
- [ ] 必备/加分技能都保留原文证据；
- [ ] 每个 `source_id/evidence_id` 都有对应 Source 节点；
- [ ] 同一岗位—技能只生成一条必备或加分关系；
- [ ] 图谱中不存在未声明的关系类型；
- [ ] `graph_import_batch.json` 能通过 `GraphImportRequest` 校验；

完成以上检查后，这批数据就可以用于 2.3 静态图谱和 3.3 初步匹配；等后续补充真实发布时间并生成连续周期快照后，再接入 3.1 和 2.4 的动态分析。
