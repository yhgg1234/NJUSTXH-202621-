## 1. 修改 `normalized_records.jsonl`

### 1.1 补回仍然漏转的技能

只修正规则映射，不需要重新做全部抽取。

当前仍有以下明确漏转：

- 4 条 IT 运维记录已有 Linux，但只放在 `tech_stacks`，导致 `skills=[]`；
- 11 处“机器学习”没有保留为 `skill:machine-learning`；
- 94 处 Go/Java 技术实体没有进入 Skill，其中 Go/go 63 处、Java 31 处。

处理规则：

```text
Linux       -> Skill
Go/go       -> Skill
Java        -> Skill
机器学习     -> skill:machine-learning
```

具体工具、语言和技术能力进入 Skill；Cloud Native、Big Data 这类技术生态进入
TechStack。

技能要求类型继续根据上游关系生成：

```text
requires -> required
prefers  -> preferred
同一 JD 的同一技能同时出现 required/preferred -> required
```

### 1.2 处理最终仍然没有标准技能的记录

使用现有标准实体、辅助列和正文兜底后仍然无法得到可靠技能的记录，可以保留
`skills=[]`，但需要设置：

```json
{
  "needs_human_review": true,
  "review_reasons": ["no_standard_skill_after_fallback"]
}
```

### 1.3 补全审核原因

所有 `needs_human_review=true` 的记录，`review_reasons` 不得为空。

若审核标记来自上游但没有具体原因，可以写：

```json
"review_reasons": ["upstream_needs_human_review"]
```

通过辅助列或正文兜底得到技能时，可以写：

```json
"review_reasons": ["fallback_skill_extraction"]
```

已有具体原因时保留原原因。

## 2. 修改 `graph_import_batch.json`

### 2.1 按岗位、月份和技能重新聚合

周期关系的聚合键必须是：

```text
(job_id, period_key, skill_id)
```

生成顺序：

```text
读取最终 JSONL
-> 根据 published_at 得到 YYYY-MM
-> 按 job_id + period_key + skill_id 分组
-> 在组内计算计数并收集证据
-> 每个唯一分组生成一条周期关系
```

补回漏转技能前，当前 JSONL 可以得到 535 个唯一的岗位—月份—技能组合。补回技能后关系
数量可能增加，因此不要写死为 535，应以最终 JSONL 的实际唯一分组数量为准。

验收时，最终 JSONL 中每个 `(job_id, period_key, skill_id)` 必须在图谱中恰好对应一条
关系，不能缺失或重复。

### 2.2 在关系 ID 中加入月份

当前格式：

```text
job:data-scientist|REQUIRES_SKILL|skill:python
```

修改为：

```text
job:data-scientist|REQUIRES_SKILL|skill:python|2023-07
```

统一格式：

```text
{job_id}|{relationship_type}|{skill_id}|{period_key}
```

### 2.3 补齐周期属性

每条 `REQUIRES_SKILL` 或 `BONUS_SKILL` 月度关系需要包含：

```text
period_key
period_start
period_end
job_jd_count
skill_jd_count
required_jd_count
preferred_jd_count
required_ratio
demand_ratio
importance
importance_method
```

时间字段示例：

```json
{
  "period_key": "2023-07",
  "period_start": "2023-07-01T00:00:00+08:00",
  "period_end": "2023-08-01T00:00:00+08:00"
}
```

`period_start` 是本月 1 日 00:00:00，`period_end` 是下月 1 日 00:00:00。

### 2.4 按月份收集 `evidence_ids`

每条周期关系的证据只能来自该关系表示的月份：

```text
evidence_ids = 当前岗位、当前技能、当前月份的去重 source_id 集合
```

每条关系必须满足：

```text
去重后的 evidence_ids 数量 = skill_jd_count
每个 evidence_id 对应 Source.published_at 的月份 = period_key
所有 evidence_id 都能找到对应 Source 节点
```

例如，`period_key=2023-07` 的关系不能引用 2023-08 或 2023-09 的 Source。

### 2.5 按固定口径计算计数和比例

```text
job_jd_count       = 当前岗位、当前月份的全部去重 JSONL 岗位记录数
required_jd_count  = 明确 required 该技能的去重 JD 数
preferred_jd_count = 明确 preferred 该技能的去重 JD 数
skill_jd_count     = required 和 preferred 的去重并集
demand_ratio       = skill_jd_count / job_jd_count
required_ratio     = required_jd_count / skill_jd_count
importance         = 0.7 * demand_ratio + 0.3 * required_ratio
```

关系类型统一为：

```text
required_jd_count > 0 -> REQUIRES_SKILL
required_jd_count = 0 且 preferred_jd_count > 0 -> BONUS_SKILL
```

一条聚合关系同时有 required 和 preferred 样本时，两个计数字段都要保留。
