## 4. `normalized_records.jsonl` 必须修改的问题

### 4.1 修正全部 `source_id`

数据契约规定：

```text
source_id = "source:" + jd_id
```

例如：

```text
jd_id     = 51job:169494577
正确ID    = source:51job:169494577
当前ID    = source:external:51job:169494577
```

当前 1000 条全部多加了 `external:`。虽然 JSONL 和图谱内部暂时能够对应，但不符合 A/B/C 三层固定 ID 规则，会影响跨批次更新和溯源。

#### 修改方法

统一使用：

```text
source_id = f"source:{jd_id}"
```

修改后必须同步重新生成：

- JSONL 的 `source_id`；
- Source 节点 ID；
- 节点 `source_ids`；
- 关系 `evidence_ids`；
- `DERIVED_FROM` 的 ID 和端点。

### 4.2 不得覆盖 2.1 的 `crawled_at`

2.1 中每条记录都有自己的 `crawled_at`。当前 2.2 把 1000 条全部替换成同一个时间，疑似使用了标准化程序运行时间。

`crawled_at` 表示数据采集时间，不是 2.2 处理时间。

#### 修改方法

- `published_at` 原样复制；
- `crawled_at` 原样复制；
- `content_hash` 原样复制；
- 如需记录标准化时间，写入 `alignment_meta.normalized_at`，不要覆盖原字段；
- 增加自动校验：同一 `jd_id` 的上述三个字段必须与 2.1 一致。

### 4.3 正确保留 `requires/prefers`

2.1 已经提供 2659 条 `requires` 和 262 条 `prefers`，但 JSONL 的 1468 个技能全部是：

```json
"requirement_type": "required"
```

#### 修改方法

必须根据 `extracted_relations_json` 中的关系类型转换：

```text
requires -> required
prefers  -> preferred
没有岗位要求语义的关系 -> mentioned 或不进入岗位技能要求
```

处理步骤：

1. 使用 `tail_mention_id` 找到关系目标实体；
2. 对实体完成标准 ID 对齐；
3. 将原关系类型写入 `requirement_type`；
4. 同一 JD、同一技能同时出现 `required/preferred` 时，以 `required` 为最终类型；
5. 即使发生合并，也要保留全部原始证据。

对于学历和证书的 `prefers`，现有图谱没有单独的 Bonus 关系类型，可以在关系 `properties.requirement_type` 或 Job 偏好属性中保留，不能直接当成硬性要求。

### 4.4 处理 316 条零技能记录

当前 316 条记录为 `skills=[]`。根据 2.1 现有数据，可以在不修改 2.1 的前提下分层处理：

| 类型 | 数量 | 2.2 处理方式 |
|---|---:|---|
| 2.1 标准实体已有 `skill/tech_stack`，但 JSONL 无 Skill | 53 | 修复映射，必须恢复 |
| 标准实体无技能，但辅助 `extracted_skills/skill_*` 有候选 | 197 | 从辅助列恢复，经原文验证后标记审核 |
| 标准实体和辅助列都无技能候选 | 66 | 从现有 `raw_text/requirements` 兜底抽取；仍没有则排除 |

换言之，至少 250 条可以直接利用现有 2.1 文件恢复，不需要让 2.1 重新处理。

当前仍有以下明确映射丢失：

- `机器学习` 丢失 14 次；
- `Go/go` 合计丢失 67 次；
- `Java` 丢失 33 次。

#### 推荐兜底顺序

1. 以标准实体 JSON 和关系 JSON 为主；
2. 若无技能，读取 `extracted_skills` 和各 `skill_*` 辅助列；
3. 辅助技能必须能在 `raw_text/requirements` 中找到证据；
4. 仍为空时，由 2.2 使用字典或模型对现有正文做一次兜底抽取；
5. 使用辅助列或二次抽取的记录标记 `needs_human_review=true`；
6. 确实无法取得技能时保留 `skills=[]`，并在质量报告中计数，不得编造。

`extracted_skills` 是类似 Python 字面量的字符串。如果使用 Python，可用 `ast.literal_eval` 安全解析，禁止使用 `eval`，并将 `C\\+\\+` 等形式规范化为 `C++`。

### 4.5 正确区分 Skill 与 TechStack

2.1 提供了 1921 次 `tech_stack` 实体。具体语言、框架、数据库和工具如果只保存在 `tech_stacks`，将无法进入 2.4 和 3.3 的岗位技能匹配，因为项目没有 `Job -> TechStack` 的岗位要求关系。

#### 修改方法

- Python、Java、Go、Docker、MLflow、Airflow、OpenCV 等具体工具统一建成 Skill；
- “云原生”“MLOps”“Java 生态”等聚合类别建成 TechStack；
- 岗位要求具体工具：`Job -> Skill`；
- 技能归属技术生态：`Skill -> TechStack`，使用 `BELONGS_TO_STACK`。

示例：

```text
Job -> MLflow(Skill)          REQUIRES_SKILL/BONUS_SKILL
MLflow(Skill) -> MLOps        BELONGS_TO_STACK
Docker(Skill) -> 云原生        BELONGS_TO_STACK
Kubernetes(Skill) -> 云原生    BELONGS_TO_STACK
```

### 4.8 合并而不是覆盖审核状态

2.1 有 102 条 `needs_human_review=true`，2.2 有 484 条。对照发现：

- 2.2 新增审核 468 条；
- 2.1 要求审核但 2.2 取消的有 86 条；
- 两层都要求审核的只有 16 条。

2.2 可以因为新候选实体或低对齐置信度增加审核，但不能静默取消 2.1 的审核标记。

#### 修改方法

```text
B.needs_human_review =
    A.needs_human_review
    OR is_new_candidate
    OR alignment_confidence < 阈值
    OR 使用辅助列/正文兜底
    OR conflicts 非空
```

同时在 `review_reasons` 或现有 `conflicts` 中写明原因，例如：

```json
[
  "upstream_review_required",
  "new_job_candidate",
  "fallback_skill_extraction"
]
```

### 4.9 熟练度和年限的处理原则

2.1 当前关系属性中的 `proficiency/min_years` 为空，因此 2.2 不能直接复制出有效值，也不能编造。

2.2 可以使用现有 `raw_text/requirements` 做二次解析：

- 只提取明确出现的“了解/熟悉/精通/专家”；
- 只把明确属于某项技能的年限写入该技能；
- 有证据才填写；
- 无法对应时保持 `null`；
- 记录抽取方法、版本和证据。

这是3.3的增强项，优先级低于 ID、时间、`prefers`和零技能修复。



### 5.4 修正 `importance` 的计算分母

当前 91 条岗位技能关系全部使用“技能计数/全部 1000 条 JD”计算需求占比，这是错误的。

例如数据科学家共有 83 条 JD，其中 43 条包含机器学习：

```text
正确 demand_ratio = 43 / 83 = 0.5181
正确 importance   = 0.7 * 0.5181 + 0.3 * 1 = 0.6627
```

当前结果为：

```text
0.7 * (43 / 1000) + 0.3 * 1 = 0.3301
```

91 条关系全部符合错误的全局分母公式，没有一条使用岗位内部样本数。

#### 正确聚合方法

聚合键：

```text
(job_id, period_key, skill_id)
```

指标：

```text
job_jd_count       = 当前岗位、当前周期有效去重JD数
required_jd_count  = 明确required该技能的去重JD数
preferred_jd_count = 明确preferred该技能的去重JD数
skill_jd_count     = required和preferred并集的去重JD数
demand_ratio       = skill_jd_count / job_jd_count
required_ratio     = required_jd_count / skill_jd_count
importance         = 0.7*demand_ratio + 0.3*required_ratio
```
